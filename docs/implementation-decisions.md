# Implementation decisions — backlog clear-out pass

- **Version**: 0.1
- **Date**: 2026-07-23
- **Context**: Autonomous pass to clear the backlog. Each decision is KISS-first and written down here so
  it can be revisited or reverted cheaply. If a choice turns out wrong, this is the place to change it.

> This log records **why** something was built the way it was (or deliberately *not* built). It is not a
> spec — the specs live in `PRD.md`, `scoring-system.md`, `minigame-catalog.md`. The authoritative status
> checklist stays in `backlog.md`.

## Legend

- **DECIDED** — chose an approach and implemented it.
- **DEFERRED** — deliberately not building now, with the reason (so it's a decision, not an oversight).

## Decisions

### D10 — Phase 5 netcode: server-authoritative + client snapshot interpolation — DECIDED

- **What**: kept the existing server-authoritative tick + throttled ROUND_STATE snapshot model (mirrors
  `../utopia-offline`: seeded determinism, ports, a mutable client render-bridge). Added a reusable
  client `SnapshotInterpolator<T>` (`game/netcode/`) that buffers the two latest snapshots and renders
  ~100 ms behind, lerping entity positions matched by stable id. This is the "client interpolation
  (~100 ms)" netcode-hardening item.
- **Why (KISS)**: no new transport, no input-prediction complexity. Interpolation alone smooths the
  ~6.7 Hz snapshot rate to 60 fps for continuous motion (falling items, a ball). Input prediction is
  only needed for the local avatar, which scenes render locally from their own input (immediate) while
  the server stays authoritative for scoring/collision — no rollback needed at party latencies.
- **Fruit Catch (`fruit-catch`, D2)** is the reference implementation: seeded falling stream, item y is
  a pure function of time (so the client can interpolate), server owns catch/score, client renders its
  own basket locally + items via the interpolator. Every later Phase 5 game follows this shape.
- **Revisit if**: a game proves latency-sensitive enough to need prediction/reconciliation (Pong at
  high RTT) — add it per-scene, not globally.

### D11 — Phase 5 games shipped in one pass; some physics is game-feel not sim-accurate — DECIDED

- **What**: all six Phase 5 games shipped — `fruit-catch` (D2), `pixel-rain` (A7), `pixel-dash` (A9),
  `snake-arena` (A8), `pixel-pong` (B1), `sumo-push` (B3). Catalog is now 25 games. Pong is a `duel`
  (reuses `pairPlayers`); Sumo is an FFA arena ranked by survival; Snake is grid-stepped
  (`Math.floor((now-startedAt)/stepMs)` — deterministic + reconnect-safe); the rest are seeded
  FFA streams following the Fruit Catch shape.
- **Physics is tuned for feel, not realism**: Pong's serve after a point is a deterministic pattern (no
  RNG in `tick`, which has no Random port); Sumo's collision uses an exaggerated restitution and a
  simple normal-component exchange rather than true elastic physics. Both are stable (speeds capped) and
  deterministic. Good enough for party games; not a physics engine.
- **How built**: the 3 latency-tolerant games (pixel-rain/pixel-dash/snake-arena) were generated by
  parallel subagents from the Fruit Catch reference + exact contracts, each creating only its 4 files
  (domain + wire + scene + test) with NO central wiring; Pong/Sumo were hand-built. All central wiring
  (registry, catalog, shared barrel, GameClient, i18n) was done in one place to avoid conflicts, then
  the whole thing verified (typecheck + determinism gate + 137 server tests + client build + Karma).
- **Revisit if**: Sumo feels floaty/sticky or Pong's serve pattern feels predictable — both are isolated
  in their domain module and safe to retune. Scene HUD status words are English literals (not i18n'd) —
  add `game.<id>.*` keys if ES coverage of those labels is wanted.

### D13 — Catalog growth: Match, Quick Draw, Pixel Roulette — DECIDED

- **What**: added three more games (catalog now **28**): `match-pairs` (A11, memory pairs — own seeded
  board, mismatch clears on the next flip so no server timers), `quick-draw` (E7, western reaction duel
  — reuses `pairPlayers`; seeded FIRE delay; false start = instant loss), `pixel-roulette` (D3, pure
  luck — seeded per-player value revealed on spin; "use sparingly").
- **How**: Match + Quick Draw via parallel subagents from the established references; Roulette by hand.
  All follow the pluggable contract with deterministic domains (seeded Random port, no wall clock),
  colocated tests, central wiring done in one place. A stray `null`-index type slip in the Quick Draw
  test (invisible to `bun test`, caught by `tsc`) was fixed by widening the local `nn` guard.
- **Revisit if**: Roulette's pure luck hurts sessions — it's opt-in per host selection and flagged
  low-priority in the ranking; drop it from default line-ups if needed.

### D12 — Final-ranking tiebreakers (points → firsts → avg position) — DECIDED

- **What**: `FINAL_RANKING` now breaks equal totals by (1) most round wins, then (2) best average
  position, per `scoring-system.md` §5. Pure service `domain/services/finalRanking.ts` (unit-tested);
  the engine accumulates the tallies per round from each round's BASE award (a "first" = sharing the
  round's top position; position is the 0-based dense rank that round). Two players share a final rank
  only when points AND firsts AND average position are all equal.
- **Why (KISS)**: reuses the per-round base points already computed; format-agnostic (FFA/team/duel all
  resolve to per-player points). Applied only at the final ranking — the between-round scoreboard stays
  points-only "current standings", matching the doc.
- **Deferred**: tiebreaker #3 (a sudden-death tiebreaker mini-game) — needs an engine sub-flow; only
  matters when players are identical on all three measures, which is rare. Left as future.
- **Revisit if**: "firsts" should exclude all-zero rounds, or team rounds shouldn't count every winning
  member as a "first" — both are one-line tweaks in `accumulateTiebreak`.

### D1 — Pixel Split cut starts at the far left — DECIDED

- **What**: the cut selector in `pixel-split` now initialises to the leftmost boundary (`cut = 1`) on
  every new object, instead of the centre.
- **Why**: a centred default already scores full points on symmetric figures, so the player did nothing.
  Forcing a left start means every figure requires a real judgment.
- **Where**: `apps/client/src/game/scenes/PixelSplitScene.ts` (`drawObject`).
- **Revisit if**: it feels too punishing on wide asymmetric objects — a middle-but-jittered start could
  be an alternative, but left is the simplest fair default.

### D2 — Simon per-pad tones via the existing SFX synth — DECIDED

- **What**: each Simon pad plays a distinct pitch on tap and during sequence playback.
- **Why**: signature Simon feel; the game already had visual-only playback.
- **How (KISS)**: added `Sfx.pad(index)` reusing the existing WebAudio oscillator helper (no assets, no
  new service). Pitches are a fixed ascending pentatonic set `[C4, E4, G4, C5]` mapped by pad index, so
  any sequence still sounds musical. Respects the existing SFX volume (the synth already gates on it).
- **Where**: `apps/client/src/game/Sfx.ts`, `apps/client/src/game/scenes/SimonScene.ts`.
- **Revisit if**: we want the authentic original Simon frequencies — swap `Sfx.PAD_TONES`.

### D3 — Phase 4 skill axes: fixed 7-axis set on `MiniGameMeta` — DECIDED

- **What**: added `SkillAxis` (`reflexes | speed | knowledge | memory | precision | nerve | focus`) and
  `SKILL_AXES` to `@pp/shared`, plus a required `axes: readonly SkillAxis[]` on `MiniGameMeta`, and
  tagged all 19 games (each ≥1 axis; every axis has ≥2 games).
- **Why**: the backlog radar proposed 6 axes but the shipped catalog needs a `focus`/attention axis
  (`color-trap`, `odd-one-out`, `number-rush`) — 7 covers everything cleanly. Tags live on the shared
  meta (not the domain module) because both apps and the engine already read `MINIGAMES_BY_ID`.
- **Revisit if**: an axis feels redundant or a new game doesn't fit — axes are data, edit the catalog.

### D4 — Radar normalization is points-relative, per round — DECIDED

- **What**: each round, a player's per-axis value is `roundPoints / maxRoundPoints` (top scorer = 1.0),
  averaged across the session's rounds that touch each axis.
- **Why (KISS)**: format-agnostic (FFA / team / duel all already resolve to award-table points), needs
  no per-game metric, and ties/averaging come for free from the existing scoring. It's a *relative*
  skill proxy, not an absolute one — good enough for a banter radar.
- **Trade-off**: the compressed award tail (10/7/5/4/3/2/2/1/1/0) means 2nd≈0.7 etc.; the radar reads
  "how you placed", not "how fast you were". Fine for presentation.
- **Revisit if**: we want true per-game normalization (e.g. reaction ms) — each game would need to
  expose a 0..1 self-score; deferred as over-engineering for now.

### D5 — Analysis rides on `FINAL_RANKING`, not a new message — DECIDED

- **What**: `FINAL_RANKING` gained optional `radars?` + `summary?` fields instead of a new
  `SESSION_SUMMARY` server message / new room phase. `PROTOCOL_VERSION` stays 1 (additive, optional,
  server→client only — old clients ignore the fields).
- **Why (KISS)**: no new client view/handler, no new phase in the state machine, one fewer wire type.
  The engine stores the computed analysis so `resumeMessages()` replays it on reconnect too.
- **Revisit if**: we later want the summary on its own screen or streamed mid-session.

### D6 — Client shows the *viewing* player's radar, not all N — DECIDED

- **What**: the final screen renders one radar — the local player's ("Your skill profile") — plus the
  session summary (most wins, biggest comeback, per-round winners). The wire carries every player's
  radar, so showing others later is a client-only change.
- **Why**: 10 radars on one screen is unreadable on mobile; a personal profile is the Brain-Training
  feel the PRD asks for. `app-skill-radar` is a dumb OnPush inline-SVG component (no chart lib), mirroring
  `PixelAvatarComponent`.
- **Revisit if**: users want to compare radars — add a player selector or a small-multiples grid.

### D7 — "Round winner" for team games = first member of the winning team — DECIDED

- **What**: the summary's per-round `winnerId` and win counts use `placements[0]`, which for a team
  round is a member of the winning team (not the team itself).
- **Why (KISS)**: keeps the summary uniformly player-centric; the team banner already lives on the
  round-result screen. Minor cosmetic imprecision on team rounds.
- **Revisit if**: the summary should credit the whole team — carry a team winner alongside.

### D8 — Phase 3 handicap: scoring lever only, config-gated, no UI yet — DECIDED

- **What**: implemented the bounded **scoring** catch-up (`applyScoringHandicap`) — trailing players earn
  a bounded bonus (default up to +20%) on their own round award, scaled by how far behind they are in
  the standings before the round. Wired into `SessionEngine.endRound` behind `SessionConfig.handicap`,
  which ships **OFF** and is set from env (`HANDICAP_ENABLED`, `HANDICAP_MAX_BONUS_PCT`).
- **Key property**: it inflates a trailer's award within a cap but never reorders a round (the leader
  gets 0 bonus; round 1 / all-level = no effect). The **radar normalizes the base award**, so catch-up
  never distorts the skill profile (see D4).
- **Why (KISS)**: lands the reusable, fully-tested core (`domain/services/handicap.ts` + tests) with a
  minimal change surface (domain + engine + config), matching the scoring doc's "ships off, tuned once
  real sessions are observed". Enabling it is an operator/env decision during tuning.
- **DEFERRED (paired, do together when handicap graduates to on-by-default)**:
  - **Mechanical per-game hooks** (leader nerf / trailer boost inside mini-games) — touches all 19 games;
    large and speculative until the scoring lever is validated in real sessions.
  - **In-UI transparency + host lobby toggle** — the scoring doc requires showing an applied bonus on
    the results screen. Not built because there is no end-user way to turn handicap on yet (env only);
    building the toggle + per-round bonus wire/UI now would be speculative. When the feature is turned
    on for players, add: `HOST_CONFIG.handicap` flag → `Room` → `LOBBY_STATE` echo → lobby checkbox,
    and a per-player bonus on `RoundResultDto` rendered as a "+N catch-up" note.
- **Revisit if**: tuning shows the points-only lever is too weak → add the mechanical hooks; or if the
  linear "distance behind" curve needs shaping (e.g. only boost the bottom half).

### D8-UPDATE — handicap toggle + transparency shipped — DECIDED

The deferred UI half of D8 is now built (the mechanical per-game hooks stay deferred):

- **Host toggle**: `HOST_CONFIG.handicap?` (optional) → `Room._handicap` → `LOBBY_STATE.handicap` →
  a lobby checkbox (`toggleHandicap`). The **room flag is the single source of truth** for on/off; the
  engine reads `room.handicap`. `HANDICAP_ENABLED` env now only **seeds the default** for new rooms
  (threaded through `LiveRooms` → `Room.create`), so a host can always override it.
- **Transparency**: `RoundResultDto.handicap?` carries the per-player catch-up bonus (non-zero only),
  rendered as a "+N catch-up" badge on the round-result screen (`room.result.catchup`). The `scores`
  already include the bonus; the badge shows how much of it was catch-up.
- **Cap** stays server-side (`HANDICAP_MAX_BONUS_PCT`). Bumped the client `anyComponentStyle` budget
  6→8 kB (warn) / 8→12 kB (error): `RoomComponent` legitimately grew with the radar + summary + toggle.

### D9 — What this pass deliberately did NOT build — DEFERRED

Cleaning the backlog also means deciding what *not* to do now. These are conscious deferrals, not
misses — each would be speculative or gated, and the project rule is "nothing built just in case".

- ~~**Phase 5 — real-time action mini-games**~~ — **NO LONGER DEFERRED**: shipped 2026-07-23 (netcode
  interpolation + all six games). See D10 / D11.
- **Phase 6 — accounts, history, DB**: this is explicitly the *first* phase to introduce a database
  (`bun:sqlite`). Phases 0–5 are intentionally in-memory/ephemeral. Adding persistence now would be a
  large architectural change with no current consumer (Phase 4 analysis renders fine from live state).
- **Remaining Phase 7 — emotes, in-room chat, public matchmaking**: social/infra features with no
  dependency from the current game loop; unscheduled. (Audio + i18n from Phase 7 already shipped.)
- **Building the rest of the mini-game catalog** (Bubble Pop E15, Match A11, Quick Draw E7, Pixel Beat
  E6, Fleet Battle C3, Sudoku Race E14, Quick Tetris E13, the racing cluster, …): the catalog is meant
  to grow **wave by wave on demand**, not all up front (`minigame-catalog.md`, `backlog.md`). 19 games
  is a strong session already. New ones are added when prioritized — several are P3/high-effort or ride
  the Phase 5 action wave. Kept as ranked ideas.
- **Revisit if**: a netcode pass is scheduled (unlocks Phase 5), long-term history/accounts are wanted
  (Phase 6), or a specific new mini-game is prioritized off the ranked list.
